The mental model

Pipeline              one drawing, one job                      (this page)
  └── Node            one step — a query, a value, a question, a decision
        ├── Its settings, in the panel that opens from the right
        ├── Its output, which every later node can read
        └── Its outputs (the dots down its right edge) — where the run goes next

A tool config is one question answered by one query. A pipeline is what you draw when the answer needs several steps in a particular order — run this, loop over what it returned, take a different path if nothing matched, ask somebody before the last step. Every one of those is control flow, and control flow is a drawing.

The run follows the lines you drew

Nothing infers an order. A node runs when something leads to it, and the run goes wherever that node's connector points. Nodes run one at a time, in sequence — there are no parallel branches.

Every node keeps its output

What a node produced stays readable by every node after it — by name, in a condition, in a parameter wiring, in a {{VARIABLE}}. That is what makes a second box worth drawing instead of a longer statement.

Nothing here writes to your data

Every SQL node is one read-only statement, checked when you save it and again on every run. Values are always bound, never spliced into the text, and no condition is ever evaluated as code.

The page is called Pipelines; the address is /graph-designer and a pipeline is stored as a graph. Same thing — the address kept its original name so existing bookmarks keep working.

The fourteen nodes, once

Add Node opens the palette. Five nodes hold something, six decide where the run goes, three act on the world or the clock. Every node also has a Label — worth setting, because every refusal and every log line names a node by it.

The three Value kinds are not decoration

All three are parsed from JSON, and the picker says which the node promises. They validate differently because a shape the node downstream cannot use is worth refusing at the form rather than halfway through a run. 

List of values   ["php", "wordpress", "laravel"]   flat, scalars only — the shape an IN takes
Array            [[1, "a"], [2, "b"]]             an array; nesting allowed. Rows, tuples
Dictionary       {"region": "north", "cap": 50}   an object. Named values
Success and Failure both have an exit. They decide what the run is reported as, and that is the first moment there is something worth announcing — so an email or a writes-a-row-somewhere step can follow the box that says what happened, rather than having to sit before it. Leaving the exit connected to nothing is the ordinary case and ends the run. What a successor cannot do is change the verdict, so one outcome node may not lead to the other — a Success drawn after a Failure would picture a green run that reports as failed.

Drawing it

The canvas arranges itself top to bottom as you build: a node you add lands where its connectors put it, and the run reads down the page. Every node shows one line of its settings under its name, and a labelled pill for each way out — a Branch's conditions, a loop's each and done, an on error. Pills sit side by side and wrap onto a second line only when they run out of room; a condition longer than its pill is shortened with an ellipsis, so hover it to read the whole of it.

Green means the node did its work; red means it could not. A node with exactly two ways out, one of them a failure, draws the other in green — a SQL node's ordinary exit, written, queued — and the connector out of the red one is red and dashed. A Branch's conditions, a loop's each and done and a union's next stay grey, because none of them says anything went right or wrong. The Success and Failure nodes are that same green and red.

Connect two nodes Either drag from a node's exit dot or branch pill and release anywhere on the target, or click the dot or pill and then click the target. Both work; clicking empty canvas cancels.
Move a node Drag it. The canvas then leaves your arrangement alone until you press Tidy up, which hands the arranging back to it.
Re-point a connector Hover it to reveal its × and its two end handles, then drag an end onto a different node.
Edit a node Its Settings button. The panel opens from the right and applies on Apply.
Move several nodes Drag a box on empty canvas to select everything it touches, or Ctrl-click nodes one at a time (Cmd-click on a Mac). Ctrl+A or Select all takes everything; Escape clears it. Then drag any selected node and they all move, connectors following. Escape mid-drag puts them back.
Move a node and the one it feeds Select the connector between them — a box drawn across it will do — then drag either node. Selecting a connector picks up both of its nodes.
Insert a node into a connector The blue + on the connector's midpoint, beside the red × that deletes it. Pick a node and it is spliced in: what was A → B becomes A → new → B, wired for you, and its Settings panel opens. A For each or Do until is joined on by its done port, so the node that used to follow still runs once rather than once per item. Success and Failure are not offered on a connector that already leads to one.
Route a connector by hand Drag the line itself and it bends through the point you drop it at, up to four bends. Drop a bend back onto the straight line to remove it, or double-click the connector to straighten it completely. Tidy up asks before straightening connectors you routed by hand.
Pick nodes to test Shift-click them, then Test selection. Scenario 15. Note this is a different thing from selecting nodes to move: shift-click picks nodes to run, Ctrl-click picks nodes to drag, and you can have both at once.
One connector per way out. Two would mean the run takes one of them and which one is not something the drawing says. To go two ways, that is what a Branch is for.

Save is not Publish. Save stores the drawing (and validates it — a refused save leaves your work on the canvas and says why). Publish is on the library page and is what makes the pipeline callable by an agent. Reload discards unsaved changes and re-reads what the database holds.
SQL 1 · A straight line

"Run last month's revenue query and record that it worked." 

Start ──→ SQL statement ──→ Success
What to fill in on the SQL node
LabelMonthly revenue
DatasourceAny relational one
Tables this statement readsorders, clients
SQL statementthe statement below
 
SELECT c.name, SUM(o.total) AS revenue
FROM orders o
JOIN clients c ON c.id = o.client_id
WHERE o.placed_at >= '2026-07-01'
GROUP BY c.name
ORDER BY revenue DESC
Tables is not bureaucracy. Nothing here parses your statement, so the list you type is the only thing that lets a table switched off in Data Sources stop this node. A node with no declared tables would make a pipeline a way around those switches rather than a way to use them — which is why the save refuses one.

One read-only statement: SELECT, or a WITH ending in one. DISTINCT, ORDER BY, LIMIT, HAVING, subqueries, CTEs and window functions are all fine; a second statement or a write verb is refused. Syntax is not checked here — dialects differ — so the run is where a typo surfaces, readably, as a failed step.

Nothing caps the rows a SQL node returns. A LIMIT in the statement is the only thing that bounds it, which puts the size of the answer where you can see it. The log is capped at 20 sample rows and always states the real total.
SQL 2 · Putting a value into a statement

"Only the department the earlier step picked."

Write :name where the value belongs, declare that name under Parameters, and say where it comes from. 

SELECT name, salary FROM employees WHERE department_id = :dept_id

The enclosing loop's item A parameter whose name is the loop's item name is filled with the current pass's item, with nothing to wire.
A declared parameter that is not wired is not a mistake — that is exactly how a value reaches the pipeline from outside, and it is what an agent's tool arguments are built from. But pressing Run on this canvas supplies no inputs, so when you are testing, either wire it or point it at a Value node.

The item's value follows one rule everywhere. A scalar item is itself. A single-column row — {"id": 7}, which is what SELECT id FROM departments yields — is that column's value, so the ordinary case needs no wiring. A row with several columns has no single value and is refused rather than guessed at, because binding an arbitrary column would filter on the wrong thing and the result would look entirely normal. Name the column in Field to pick one.
One value, or the whole list
Takes Write it as Runs
One value (default) dept_id = :dept_id once, with a plain scalar bound
All the values, as a list dept_id IN :dept_ids once, for the whole list
Written as IN :name, never IN (:name). A list parameter renders its own parentheses, so the second is a syntax error. Getting it the wrong way round in either direction is refused when you save — because the alternative is a syntax error the database reports mid-run, long after the panel that caused it was closed.

:name, with no space after the colon. where id = : dept_id is refused too, and it earns its own check: the space hides the placeholder from every other rule here, so the statement would save clean as one that uses no parameters at all and then come back from the database quoting ': dept_id'.

The statement is never rewritten. Values are bound by the driver, so what runs is the text you approved.
Control flow 3 · A branch

"If the check found anything, email it. Otherwise stop quietly." 

SQL ──→ Branch ──found──→ Send an email ──→ Success
                 └──else───→ Success
The condition row

Outcome namefound — this becomes the branch pill's label
The eight comparisons
is equal to        is not equal to
contains           does not contain
is empty           is not empty          ← compare against nothing
is greater than    is less than
Conditions are compared, never evaluated. Every comparison is a name from that fixed list and it happens in Python — there is no expression language on this path and nothing reaches eval, so a pipeline cannot be used to run arbitrary code even by the person who drew it.

0 and false are not empty. A query returning a count of zero has produced a real answer, and treating it as empty would send the run down its nothing-found path when the thing it found was zero.

Conditions are tried in order and the first match wins. else is always there and is where a run goes when none matched — so it is worth connecting even when you think it cannot happen. Two conditions may not share an outcome name, and none may be called else.
Loop 4 · For each — one pass per row

"For each active department, the highest-paid employee." 

departments ──→ For each ──each──→ top earner (SQL) ──┐
                    │                                │
                    └──done──→ Success               └──→ back to For each
What to fill in on the loop
Loop over the result ofthe departments SQL node
Call each onedept
Most passes allowed200 — the default
And on the body's statement
SELECT name, salary
FROM employees
WHERE department_id = :dept
ORDER BY salary DESC
LIMIT 1

The parameter is called dept — the loop's item name — so it fills itself from the current pass with no wiring at all. That works because SELECT id FROM departments yields single-column rows; for a wider row, wire the parameter to the loop and name the column in Field.

The body must lead back to the loop. This is the mistake worth knowing about, because nothing about the drawing looks broken: the loop has a source, a ceiling and a body wired onward to Success. What happens is one pass, and then the run carries straight on — one pass of eighty-two, reported as a success, with nothing in the log saying the other eighty-one were never attempted. So a save refuses a loop with nothing on each, or a body with no edge back. Any edge back counts, from any port.

A cycle needs a loop node on it. A plain A → B → A is refused: it has no cursor and no ceiling, and what stops it is an internal error a long way from the two lines that caused it. A cycle through a loop's done port is refused too — done is the way out.

The ceiling refuses rather than truncating. Rows from the first two of three departments are indistinguishable from rows for all three, and a total over them is a plausible number that is wrong. The run stops and names the node.
Loop 5 · Keeping every pass, not just the last

Scenario 4 as drawn has a flaw you only notice after done: a node's output is keyed by the node, so pass 82 overwrote pass 81. Two optional fields on the For each fix it.

Collect the result of the top earner node. Every pass's rows are put together.
Record the item as department_id — a column added to each collected row, holding the item that produced it.
The loop's own output becomes the union once the loop is over. While it turns, reading the loop gives you the current item; on the visit that leaves by done it is the collected rows. So a node after done wired to the loop reads every pass, as rows — a condition, a parameter, another loop and the dock's preview all work with nothing further arranged.

"Record the item as" is how you keep the result readable. Rows from twenty passes of one statement are otherwise indistinguishable once concatenated — filtering on a department without selecting it is perfectly ordinary SQL. Leave it blank only when the statement already returns the value; asking for a name the statement already returns is refused as a column collision rather than one value quietly replacing the other.

Only a node inside the body may be collected. One outside it ran once, before the loop, so every pass would append the same rows — and a union of duplicates looks exactly like a union. The picker offers exactly the nodes that qualify, which is also why it looks empty until the back edge is drawn. A Do until cannot collect at all: only a loop that knows which pass is its last can publish a union.
SQL 6 · One query instead of N

"Every employee in any of those departments."

A loop is N round trips. When every item goes into the same comparison, you do not need one — set the parameter's Takes to All the values, as a list and drop the loop entirely. 

departments ──→ SQL ──→ Success

SELECT name, department_id FROM employees WHERE department_id IN :dept_ids

SQL Loop 7 · The Union node — one statement built per pass

"Eighty-two departments, a different fragment per department, and I want one round trip."

A Union node is a SQL node that does not run when it is reached. It sits in a For each body, adds one copy of its statement per pass, and on the pass the loop hands it the last item it runs the whole thing as a single query — leaving by execute instead of going round again. 

select id from departments        82 ids
        │
   ┌────▼─────┐  each   ┌───────────────┐
   │ For each │────────►│ Union         │  next ──┐  appends fragment 1…81
   │          │◄────────┤               │         │
   └────┬─────┘         │  execute ─────┼──► runs fragments 1…82 as one query
        │ done          └───────────────┘
        ▼
   (only reached when the list is empty)
Values are still bound. This is the only place in the application that writes SQL, so it is worth saying how it stays safe: each pass's copy has its placeholders renamed — pass 7's :id becomes :id__p7 — and pass 7's value is bound under that name. Eighty-two fragments carry eighty-two bind parameters and no value is ever written into the text. (A parameter you name id__p7 yourself is refused at save: it would collide with a generated name and one pass would be filled with another pass's value.)
Three rules, each with a reason:
  • It must sit inside a For each body. Which pass of how many is a fact only a loop's cursor has. Outside a loop the node would add one fragment, take next, and the statement it built would never run — a silent nothing from a box that says it succeeded. A Do until cannot host one either.
  • No ORDER BY or LIMIT in the fragment. Unparenthesised, either binds to the whole union rather than the member it was written on, so it would quietly sort or truncate every pass at once. Sort or cut in a node after execute.
  • The length ceiling refuses rather than truncating. A union short of its last fragments is short of whole departments, and no row count says so.

A query that failed takes the on error path, never execute — a query that did not run cannot leave by the port that means "here are the rows".
Loop 8 · Do until

"Keep re-checking until the backlog is clear."

A For each loops over a list it was handed. A Do until loops over nothing in particular and stops when a condition becomes true — the same condition row a Branch uses, under Repeat until this is true. 

Do until ──body──→ re-check (SQL) ──→ back to Do until
    │
    └──done──→ Success
A condition that never becomes true stops at Most passes allowed and says so, naming the node — it does not run forever and it does not report success. The same body-must-lead-back rule as scenario 4 applies. And a Do until cannot collect and cannot host a Union node: it learns which pass was its last only after that pass has already run, so there is no visit on which it could publish anything.
People 9 · Ask a person mid-run

"Show me what it found and let me confirm before it emails anyone."

Question "18 clients would be emailed. Go ahead?" — a {{VARIABLE}} is allowed here, so the figure can be the real one
Answer Yes or no · One of a list · Free text
Choices Comma separated. Only used for "one of a list".

The run parks. The question appears above the dock whichever tab you are on, and the run resumes when you answer. An answer that does not fit is refused while you are still looking at the prompt, rather than failing a node three steps later.

The same node works inside a conversation. When an agent calls a published pipeline that pauses, there is no dock — so the question is handed to the model to relay word for word, and a companion answer_… tool resumes the parked run on a later turn. It is not paraphrased, because a reworded question asks the user something else. That answering tool is offered only when the pipeline actually contains a question node.

One exception worth knowing: Let an agent read and filter its whole result (scenario 16) refuses a pipeline that stops to ask, quoting the question — reading a whole result set and holding it across two turns are two different shapes.
Failure 10 · When a node fails

A SQL, Union, Tool config or Email node has a second output — on error / not sent. Whether you connect it changes what a failure means.

You drew… …and the node fails
nothing on on error The run ends and is reported as failed, with the node's message.
an error path The run takes it. The run is not marked failed — you said what to do about it. The step is still logged as failed, so the log does not hide it. 
SQL ────→ Success ──→ Send an email  ("the nightly check passed")
 │
 └─on error──→ Failure ──→ Send an email  ("the nightly check did not run")
"This node failed and we handled it" and "this run failed" are different facts, which is why they are recorded separately: a pipeline that recovered from a failed node reporting the whole run as failed would be the opposite of what drawing a recovery path means.

Because both outcome nodes have an exit, the announcement can sit after the box that says what happened — which on the failure side is the only order that reads correctly.
Clock 11 · Timing something

"How long did the export part take?"

A Timer is a stopwatch: one node type carrying four actions. The instance set to Start is the timer; the other three point at it by picking it from a list, so a save can prove the reference is real. 

Timer (Start) ──→ …work… ──→ Timer (Stop, pointing at the Start) ──→ Success

Pause and Resume bracket a stretch that should not count —
a question you are waiting on a person to answer, say.
What a Stop publishes
{"started_at": "...", "ended_at": "...", "elapsed_seconds": 3852.117,
 "total_elapsed_seconds": 3852.117, "paused_seconds": 40.0,
 "elapsed_human": "1h 4m 12s", "running": false, "phase": "stopped"}

elapsed_human is there because the obvious thing to do with the number is put it in a sentence — {{ELAPSED}} in a Success message, bound to that field. The datetimes are deliberately not formatted for a reader: that needs a timezone and a locale, which belong to whoever is reading, not to the run.

Every illegal transition is refused, never quietly ignored — pausing a paused timer, resuming a running one, stopping one twice, acting on one never started. A timer that silently ignored a Stop would report a number that looks plausible and is wrong.

Starting one twice is refused — except inside a loop body, where it means "this pass begins now": the timer restarts, elapsed_seconds answers "how long did this pass take" and total_elapsed_seconds answers "how long has the loop spent in here altogether".

Two things the save refuses outright: a Pause/Resume/Stop its Start cannot reach by any path (provably dead — no run could have started the timer before arriving), and one inside a loop body whose Start sits outside it (green on pass one, red on pass two — the worst failure mode available). A Start with no Stop is fine: a pipeline that only wants to know when something began is a legitimate pipeline.
Clock 12 · Waiting

One field: Seconds to wait. At most 900 (15 minutes).

A waiting run does not survive a restart. A deploy landing inside a wait leaves the run cancelled, and nothing resumes it. That is the first thing to know about the node, and it is the price of not building a second scheduler — for anything measured in hours, use an Integrations schedule, which is persisted.

Longer than 900 is refused at save, never clamped: a drawing saying two hours while the run waited fifteen minutes is a picture that lies about the run, which is worse than a refusal that explains itself.

One consequence for a pipeline an agent calls: the agent waits about 90 seconds, so any wait beyond that makes the tool report "still being worked out" rather than an answer.
Advanced 13 · {{VARIABLES}} — a value inside the text

"The table name is different per region, and I do not want eleven near-identical nodes."

A parameter puts a value into a statement. A variable puts text into the text — a table name, a figure in a message, a number in a question. Declare it under Variables on the node, then write {{NAME}} in one of that node's variable-enabled fields (the panel lists which). 

SELECT region, SUM(total) FROM {{TABLE}} GROUP BY region

Variables
  TABLE   From: An earlier node's output   Node: regions   Field: rows[0].table_name
          If it has no value: Fail and name the variable
Which fields take one

This is substitution, not evaluation. There is no expression language, no filters, no conditionals. {{NAME}} is replaced by a value a binding resolved, and everything else in the text is text.

A variable with no value: you decide which. Fail and name the variable, or use this default. The presence of a default is the switch — an empty default and no default are different instructions, which is why it is a picker rather than a text box.
In a SQL statement, a variable is for an identifier — never a value. A bind parameter already expresses every value and the driver binds it, so it cannot change what the statement does. The one thing a bind parameter cannot express is a name: no driver lets FROM :table name a table. Four rules keep it there:
  • A {{NAME}} inside a string literal or a comment is refused at save — that is somebody reaching for it to do a value's job.
  • A substituted value must be a name or a whole number — a dotted identifier up to three parts, or up to 18 digits. That refuses a space, a quote, a semicolon, a parenthesis and the empty string. It applies to fixed values too.
  • The statement is re-checked after substitution, so a second statement or a write verb is still refused.
  • The table list still binds. A substituted table name must still appear in Tables this statement reads, and a table switched off in Data Sources still stops the node.

Two consequences: a value that renders a :something into the text becomes an unbound placeholder and the driver errors; and a variable named UPDATE or DELETE is refused by the write-verb check, so name it something else.
Acts on the world 14 · Sending an email

A Send an email node sends an email template through one of your SMTP servers.

TemplateWhat the email says. Editing it later does not change emails already sent.
Send throughAn SMTP server.
To / Cc / BccComma separated. At least one To. Each entry may be a fixed address or a {{VARIABLE}} the template declares.
VariablesOne row per variable the chosen template declares — from an earlier node's output, or a fixed value.
An Email node has no Variables section of its own, and declaring one there is refused. Its variables come from the template, and a substitution pass here would eat {{CUSTOMER}} before the email renderer ever saw it.

The not sent output is for a refusal knowable now — an unresolvable binding, a switched-off template. A relay bouncing the message tomorrow is not knowable now and cannot route anywhere on this canvas; that lives in the delivery log.

A template you own but have shared with a team is still yours to send — sharing a template does not remove your own access to it.
Acts on the world 17 · Writing a file, and emailing the link

A Create a file node writes an earlier node's rows to a file. A Download a file node turns that into a link you can fetch — and that an Email node can send on.

                                 node's rows      output              to it
Rows fromThe node whose output holds the rows. A SQL node's output is every matching row, so the file holds the lot.
FieldOptional. A path into that output, such as rows. Leave it empty to write the whole output.

The Download node's output carries url, file_name, row_count and expires_at — bind an Email node's variable to url to send the link on.

The link is yours, not the world's. It needs you to be signed in, so it belongs in an email to your own team rather than to a customer. It lasts a day.

There is no download button here. A pipeline has no chat for one to appear in, and the canvas says so if a graph arrives carrying button settings. The chat button belongs to the Flow Builder's version of these blocks.

Nothing is ever trimmed to fit. A result past 500,000 rows fails the node rather than writing the first 500,000 — a file that looks complete and is not would be sent on by somebody with no way of knowing. Draw the failed path.

Node status is painted back onto the canvas as the run moves, which is what makes the page a monitor rather than a diagram. A node inside a loop has one box and one row per pass, so the box shows its latest pass and the dock lists them all. Drag the dock's top edge to resize it.

Nodes you left out get a "skipped" row, because a node missing from the log is indistinguishable from one the run never reached. And a node in your selection that reads a node outside it fails, naming what is missing — a loop over an absent list would otherwise loop zero times and report success, which is a green tick on a test that tested nothing.

The preview always states the real count, not the sample size: twenty rows shown, two thousand reported, if that is what happened.
Running 16 · Publish, and who may call it

A pipeline is callable by a data agent when both are true: it is published, and it has an attachment. Two switches rather than one, so a pipeline can be parked mid-edit without losing its attachment, and a draft can sit attached while it is finished.

Where Control What it does
The library row Publish / Make Draft Publishing validates the drawing, so it can be refused — the reason lands above the table.
The Edit dialog Data agent One agent, and one pipeline per agent. Adding a new agent means attaching one to it.
The Edit dialog Workspace Every agent in that workspace can call it — including agents added next month, with nobody attaching anything. That is the whole point of it.
The Edit dialog Let an agent read and filter its whole result Off by default. See below.
The two attachments are mutually exclusive, and setting either clears the other. Holding both would hand the same pipeline to one agent twice — once as its own, once through its workspace — and a model offered two identically named tools cannot choose between them. The Callable by column names whichever is set.

One name per shelf. A pipeline's tool name comes from the name you wrote, so "Monthly revenue" and "monthly-revenue" both become monthly_revenue. Attaching the second is refused, quoting the first. Drafts count, since a colliding draft becomes a live collision the moment somebody presses Publish.

The description is what the model routes on, so write it as the question the pipeline answers — the same advice a tool config's description gets, for the same reason.
"Let an agent read and filter its whole result" lets an agent answer questions the pipeline itself takes no parameter for — "revenue for the Python department in March" against a pipeline that returns every department and every month. Every record is read, so the answer states the exact number that matched rather than a number counted off a sample.

It is off by default, and it means slightly more here than on a tool config: a tool config is one statement, while a pipeline can be a loop over eighty-two departments, so "run the whole thing and hold the result" is a larger promise. A pipeline that stops to ask a question is refused on this path, with the question quoted.

What the model is told is the last node that produced data, not simply the last node to run — a pipeline almost always ends at a Success node, and reporting {"succeeded": true} would describe a run that read two hundred rows as having returned nothing.

A worked pipeline

What a real one looks like end to end — a nightly check that emails only when there is something to say, and reports either way. 

Start
  └→ Timer (Start)                       label: "clock"
      └→ stale_projects (SQL)            projects with no update in 30 days
          ├─on error──→ Failure ──→ Send an email  "the nightly check did not run"
          └→ Branch
               ├─found──→ For each  over stale_projects, call each one "proj"
               │            each ──→ owner_of (SQL)   WHERE project_id = :proj
               │                       └──→ back to For each
               │            done ──→ Ask a human  "{{COUNT}} owners will be emailed. Go ahead?"
               │                       └→ Send an email
               │                            └→ Timer (Stop, → clock)
               │                                 └→ Success  "done in {{ELAPSED}}"
               └─else───→ Success  "nothing stale"
Node Why it is a separate box
stale_projects Its result is read three times — by the branch, by the loop, and by the count in the question.
Branch So a quiet night reports success instead of emailing nobody about nothing.
For each + Collect the result of The per-project statement differs, and every pass's rows are wanted — not just the last.
Ask a human The one step that touches people outside the team. {{COUNT}} makes the question the real one.
The on error path A check that failed silently is worse than one that failed loudly; the Failure node's exit is what carries the alert.
Timer So "done in 4m 12s" is a measurement rather than a guess — and the pause while a person answers can be bracketed out.
