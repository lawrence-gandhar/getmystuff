All three run for real against the SQLite test database — validation, ownership

Emphasis went where getting it wrong is expensive:

- **`validated_query_config`** is the one validator both the query builder and the
  AI SQL assistant funnel through, so a config the model produced has to be
  exactly as trustworthy as one a human built. Its rejection cases — unknown
  keys, section size caps, aggregation functions, filter operators, and column
  names that could terminate an identifier — are covered exhaustively.
- **`update_tool_config` returning two agent ids** when a tool moves between
  agents. The agent it *left* is still describing that tool in its routing
  prompt; returning only the destination would leave a stale prompt advertising a
  capability the agent no longer has.

  datasource, and an agent's workspace and AI key, are all re-resolved with an
  ownership filter rather than trusted from the form. Every one of those has a
  test pasting another user's uuid.

## Findings added this run

### 6. Datasource names are unique across every tenant, not per user

`app/models/datasource/datasource.py:88-93`

`uq_datasource_name_lower` indexes `lower(datasource_name)` alone, with no
`user_id` column. Once one customer creates a datasource called `sales_data`, no
other customer can ever use that name — and the 409 they receive tells them a
name they cannot see is already taken.

Every comparable table gets this right: workspaces, data agents and tool configs
all scope their unique index to the owner (`uq_workspace_user_name_lower`,
`uq_data_agent_user_name_lower`, `uq_tool_config_agent_name_lower`). This one
looks like it was simply missed. Verified directly against the test database — a
second user inserting `SALES` after the first inserted `sales` raises
`IntegrityError`.

Fix is a migration plus a model change. Pinned by
`tests/unit/services/datasource/test_datasource_service.py::TestDatasourceNamesAreGloballyUnique`.

### 7. `create_datasource` swallows its own error messages and returns `False`

`app/services/datasource/datasource_service.py:118-143`

When metadata collection comes back empty, the function deletes the row and
raises a carefully-worded `HTTPException(400)`: *"We connected to the database
successfully, but could not read any tables or collections from it…"*.

That `raise` is inside the same `try` whose final clause is:

```python
except Exception as e:
    print(str(e))
    return False
```

`HTTPException` is an `Exception`, so the 400 is caught, printed to stdout, and
the caller gets `False`. The message written for this exact situation can never
reach a user, and the failure is signalled by a falsy return value rather than an
exception — which CLAUDE.md forbids outright ("No silent failures are allowed.
Every failure must raise an exception with a clear human readable message"). The
`print` is also the only diagnostic; nothing is logged.

Fix: re-raise `HTTPException` ahead of the bare handler, or drop the bare handler.
Pinned by `TestCreateDatasourceSwallowsItsOwnErrors`.

### 8. Table search is case-sensitive despite claiming otherwise

`app/services/datasource/datasource_service.py:513-514`

The comment reads `# SEARCH (substring, case-insensitive)`, but the code is:

```python
live_tables = [t for t in live_tables if search in t.lower()]
```

It lowercases the *table name* and not the *search term*, so any query containing
an uppercase letter matches nothing. Typing "Cust" in the UI silently returns an
empty list. Fix is `search.lower() in t.lower()`. Pinned by
`TestSearchSortTables::test_search_is_case_sensitive_against_the_table_name`.

### 9. The `configuration_data` toggles return `None` instead of raising

`app/services/datasource/datasource_service.py:416-417, 459-460, 496-497`

`toggle_column_status_service`, `toggle_table_status_service` and
`search_sort_tables` return `None` / `[]` for a datasource the caller does not
own, where every other function in the module raises 404. Worse, the same `None`
also means "refused because the parent table is inactive", so a route cannot tell
an authorization failure from a legitimate business rule. Lower severity than the
above — no data leaks either way — but it is the same silent-failure pattern.
Pinned by the ownership tests in `TestToggleColumnStatus` and
`TestToggleTableStatus`.

### 1. The RDBMS / Mongo circuit breaker raises instead of tripping — and a failed connection test 500s

`app/db/db_utils.py:31-32,185-186`

`CIRCUIT_FAILURE_LIMIT` and `CIRCUIT_RESET_SECONDS` are read with `os.getenv`
and never cast, so they are `None` when unset and `str` when set.
`_register_failure` then evaluates `wrapper.failures >= CIRCUIT_FAILURE_LIMIT`
— `int >= None` — and raises `TypeError`.

Two consequences:

- The circuit breaker is dead code. It can never open, so an unreachable
  user database is retried indefinitely.
- `test_rdbms_connection` and `test_mongo_connection` are annotated `-> bool`
  and documented to return `False` on failure. They call `_register_failure`
  from inside `except`, so on the failure path they **raise `TypeError`**.
  A user who enters a wrong database password gets an unhandled 500, not the
  "Datasource connection failed. Please verify credentials." message CLAUDE.md
  requires.

Verified directly:

```
[test_rdbms_connection] Connection failed: OperationalError: unable to open database file
RAISED: TypeError '>=' not supported between instances of 'int' and 'NoneType'
```

The file-datasource half of the same module already does this correctly
(`_FILE_CIRCUIT_FAILURE_LIMIT: int = int(...)`, line 783), so the fix is to
mirror it. Pinned by `tests/unit/db/test_db_utils_pool.py::TestCircuitBreakerIsBroken`.

### 2. `openpyxl` is not installed and is declared nowhere — every Excel upload fails

`requirements.txt` / `requirements-dev.txt` / `pyproject.toml` / `Dockerfile`

The application calls `pd.read_excel` / `pd.ExcelFile` in six places
(`app/db/db_utils.py:1049,1119,1200,1270`, `app/routes/datasource/datasource_routes.py:85,225`)
and advertises XLSX as a supported upload type (CLAUDE.md; the `"xls"` entry in
`app/utils/file_utils.ALLOWED_EXTENSIONS`). pandas needs `openpyxl` to read
`.xlsx`, and it is installed nowhere and declared in no requirements file, so
every Excel datasource fails at runtime with `ModuleNotFoundError`.

Deliberately **not** worked around by adding it to `requirements-dev.txt`: that
would turn the Excel tests green while production stayed broken. The three
Excel tests skip with this reason instead, so the gap is visible in every run's
output. Pinned by
`tests/unit/db/test_db_utils_file_datasources.py::TestFetchFileListing::test_the_excel_engine_dependency_is_missing`.

### 3. The JWT signing key is a hardcoded literal

`app/db/auth/auth.py:20`

```python
SECRET_KEY = "super-secret-key"   # CONFIG (Move to ENV in production)
```

The module's own comment flags it; it was never moved. The key is committed to
the repository and identical in every deployment, and it is the only thing
standing between an attacker and a forged session cookie — anyone with source
access can mint a valid `access_token` for any user uuid. A test demonstrates
the forgery rather than asserting it in prose.

`FERNET_KEY` and `DATABASE_URL` are already read from the environment; this
should be too, failing startup when unset. Pinned by
`tests/unit/db/auth/test_auth.py::TestHardcodedSigningKey`.

### 4. `authenticate_user` ignores `is_active`

`app/db/auth/auth.py:97-113`

A deactivated account can still exchange its password for a token: the lookup
filters on `email` only, and neither `get_current_user` nor `require_auth`
checks `is_active` afterwards either. Whether that is intended depends on what
the flag is meant to gate, but nothing in the auth path enforces it today.
Pinned by `test_auth.py::TestAuthenticateUser::test_an_inactive_user_still_authenticates`.

### 5. A non-string `datasource_name` escapes as a raw `AttributeError`

`app/schemas/datasource.py:35`

`_normalize_datasource_name` runs under `mode="before"`, so it receives the raw
value and calls `.strip()` on it. For `None`, an int, a list or a dict that
raises `AttributeError`, which Pydantic does **not** wrap into a
`ValidationError`. A route catching `ValidationError` — the normal pattern —
does not catch it, so a JSON body containing `"datasource_name": null` yields
`'NoneType' object has no attribute 'strip'` instead of a usable message.
Conflicts with CLAUDE.md's human-readable-error rule. Fix is a type check, or
`mode="after"`. Pinned by
`tests/unit/schemas/test_datasource_schema.py::TestRejection::test_a_non_string_escapes_as_a_raw_attributeerror`.
